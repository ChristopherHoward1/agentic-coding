# Plan

One screen, always. Reasoning lives in work units — link, don't restate.

## Objective

An end-to-end agentic development framework for a solo developer: skills-driven plan/implement/review loop, mechanically enforced writer≠reviewer, deterministic gate, worktree isolation. Thin by design — framework work stops the moment real use stops demanding it.

## Decisions

- 2026-08-15 — No custom runtime; Claude Code is the orchestrator (Overstory's archival was the cautionary tale) — `3b80c19`
- 2026-08-15 — Gate is a shell script with an exit-code contract; agents never overrule it — `3b80c19`
- 2026-08-15 — knowledge/ starts empty; docs earn their way in — `3b80c19`
- 2026-08-16 — Merge autonomy: confirm-then-push (C), auto-promoting to full TRIP (A) after 4 releases where the confirm changed nothing — `work/trip-release`
- 2026-08-16 — CalVer, not SemVer; all release preconditions enforced by `release.sh` exit codes, never skill prose — `work/trip-release`
- 2026-08-16 — Release validates ARCHI freshness but never regenerates it; `/compact` stays the only ARCHI pipeline — `work/trip-release`
- 2026-09-08 — Handling a reviewer CRITICAL/HIGH the orchestrator believes is wrong: analyze it on the merits, weigh the *other* reviewer's independent severity on the same behavior, escalate the open finding to the Owner, and override only with the analysis recorded in the plan's Review section — never ship a regression to appease a reviewer. First exercised rejecting codex's three-dot-merge-base false positive — `work/review-diff-base-origin-main/retro.md`
- 2026-08-24 — `work` profile for Atlassian/Bitbucket: config-selected release topology (self ff-merges main; platform-team fetch-guards `origin/main` + pushes a branch for PR), one template not a fork — `work/work-profile` *(topology superseded 2026-08-25)*
- 2026-08-25 — One universal PR-merge release topology under protected `main`; `self` direct-push + `review.human_pr_review` knob removed; tagging moves post-merge to `release.sh tag-after-merge` (verify-then-tag, no push) — `work/pr-merge-topology`
- 2026-08-26 — /5-retro stage; release.sh refuses unit N until unit N−1's retro exists non-empty — work/retro-stage
- 2026-08-26 — README loop/skills sections are release-note-owned: checked at /4-release step 3, fixed via the small-fix path — `work/retro-stage/retro.md`
- 2026-08-26 — codex reviewer command is main-bound (branch config cannot choose the reviewer binary); marker byte-identity vs origin/main — work/loop-hardening
- 2026-08-27 — A test asserting a guard exists is not done until it has been shown to fail with that guard removed; a green suite cannot distinguish a real case from a vacuous one — `knowledge/test-helper-contract.md`, `work/ds-hygiene-hook/retro.md`
- 2026-08-27 — A handoff citing a `PLAN.md` decision must also name the `knowledge/` doc that says how to satisfy it; cold-tier docs load on citation only, so an uncited doc does not exist for a cold implementer — `work/gate-tool-preflight/retro.md`
- 2026-08-27 — A plan-reviewer's "drop this marginal fix" is a cost signal: keeping a flagged-inert fix tends to spend its savings back as review-round churn (fix 3 drew 3 of 4 rounds) — `work/loop-hardening/retro.md`
- 2026-09-01 — A unit that adds/renames a `scripts/` or `skills/` file must refresh `ARCHI.md` **on the release branch** with a targeted edit: `release.sh` checks ARCHI freshness on the branch, and `/compact` from a `main` checkout cannot describe branch-only code, so "run /compact" is not the remedy here — `work/exec-state/retro.md`
- 2026-08-28 — A guard is not pinned until a mutation to it has been shown to fail the suite **and** that mutation was verified to have landed; writing the doc then citing the doc did not stop a third consecutive unit shipping unpinned guards, while reviewer-run mutation testing caught every one — `knowledge/silent-no-op-hazards.md`, `work/work-artifact-capture/retro.md`
- 2026-09-08 — The orchestrator keeps the primary checkout on a clean `main`; transient status notes (e.g. a "now implementing" `PLAN.md` edit) never live uncommitted in the primary tree. Both `/4-release` (`main must be checked out in the primary worktree`) and branch switches require it, and a stale feature-branch checkout also stale-bases the review diff — self-inflicted friction that recurred across two units before earning this rule. The same applies to local commits on `main`: any `PLAN.md` edit a unit needs goes on its branch, because a local-only `main` commit breaks `/4-release`'s `--ff-only` pull. Plan review caught a plan that did exactly this — `work/archi-fresh-in-review/retro.md`, `work/harness-install/retro.md`
- 2026-09-04 — Plan footprints name the **canonical tracked path** (`skills/…`, `agents/…`), never the `.claude/` symlink alias: a cold reviewer sees the plan's path string vs the diff's and cannot be relied on to resolve the symlink, so the alias reads as a phantom footprint violation (noted benignly in `codex-verdict-medium`, then a blocking HIGH costing a round in `implementer-ladder`) — `work/codex-verdict-medium/retro.md`
- 2026-10-09 — A unit's `wt/<slug>` branch reaches `main` only through its `/4-release` PR; never open or merge a PR for it straight after `/2-implement`. PR #45 merged the pre-review docs-stage implementation, so the round-1 fixes and review record sat on the branch for 18 days. `release.sh`'s sentinel check caught it, and the earlier clean-up check wrongly reported the unit as already on main — `work/docs-stage/retro.md`
- 2026-10-09 — After a release PR merges, delete the primary checkout's untracked `work/<slug>/` copies before `git pull --ff-only`, first checking each one against `origin/main`. They would otherwise block the fast-forward — `work/acceptance-demo/retro.md`
- 2026-10-09 — If a release PR's CI fails, never stack a fix on top of the `Release v<version>` commit, because `tag-after-merge` needs that commit at the tip. Drop it on the branch, commit the fix, run a fresh review round (the orchestrator is now the writer), re-run `release.sh`, then `--force-with-lease` push the PR branch — `work/template-export/retro.md`
- 2026-10-09 — The orchestrator never writes `Plan verdict: APPROVE`. That line records only the plan-reviewer's APPROVE, or follows an explicit Owner approval line. After REVISE, the plan stays `draft` until one of those exists. Seen twice (`acceptance-demo`, `template-export`) — `work/template-export/retro.md`
- 2026-10-09 — At session start, `git fetch` and `git pull --ff-only` the primary checkout before reading the hot tier or loading a skill. A stale `main` made a merged retro look missing, and made `/4-release` run from pre-pull skill text that skipped the README-drift step. — `work/template-sync/retro.md`
- 2026-10-18 — The template becomes a standalone harness with **zero work-repo footprint**: it's cloned from the public `agentic-coding-template` into the Owner's home, nothing harness-related is committed to work repos, and the gate runs locally (the work firewall blocks CI → GitHub). Work projects drop VERSION, CHANGELOG and tags, and the PR is the record. - 2026-10-18 — `harness-install` split: the registry and project root ≠ git root go to `harness-registry` (plans and sentinels flow as branch commits, so they need their own design); the gate-SHA record goes to `pr-release`; this repo keeps `ci.yml`; all skills install globally, alongside Claude Code's built-in `/init` and `/compact` — `work/harness-install/plan.md`

- 2026-10-19 — The pre-push work-term denylist is dropped from `harness-publish`: the Owner never pushes harness changes from work machines; work friction is written down there and fixed in this repo. The guard design survives in the plan's Review section — `work/harness-publish/plan.md`

## Risks

- Correlated validators: mitigated 2026-08-26 by the codex second reviewer (`work/codex-reviewer`); residual — orchestrator and Claude reviewer still share a vendor, and codex's read-only sandbox can't run the gate, the demo or mutations, so all runtime evidence comes from the Claude reviewer alone (`work/acceptance-demo/retro.md`).
- The PR-merge flow's `tag-after-merge` verify assumes the PR lands as a fast-forward/rebase so `origin/main`'s tip stays the `Release v<version>` commit; a merge-commit or squash strategy would (correctly) fail the guard and block tagging.
- `harness state` is accurate only for in-flight units and the latest release: earlier released units report `stage: release`, and plans approved over a REVISE before 2026-10-18 report `stage: plan` (they predate the `Owner approval` line).
